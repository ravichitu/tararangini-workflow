# GitHub Source Control and Web Updates

## Repository separation

Use two repositories:

| Repository | Visibility | Contents |
| --- | --- | --- |
| `ravichitu/billing-jobintake` | Private | Source code, tests, safe documentation, GitHub Actions workflows |
| `ravichitu/tarangini-suite-updates` | Public | Signed installers, `latest.yml`, blockmaps, SHA-256 report, release notes only |

The update repository never contains databases, customer attachments, backups, JWT secrets, device identities, release certificates, or source code. The source repository has fresh Git history so historic data files from the old repository cannot be carried forward.

## Bootstrap release

Version `1.2.0` is the first build containing the web updater. Install it manually on the Main System and clients. From `1.2.0` onward, each installed desktop checks the public update feed at startup and every six hours. It only downloads after a user action and only installs after the local client has no pending or conflicted offline items.

## Required GitHub configuration

1. Keep `billing-jobintake` private as the source repository.
2. Use `tarangini-suite-updates` as the public, installer-only repository. Public access permits update checks without putting a GitHub token on customer computers.
3. In the private source repository, add these Actions secrets:
   - `TARANGINI_UPDATES_TOKEN`: fine-grained token limited to **Contents: Read and write** on `tarangini-suite-updates` only.
   - `TARANGINI_CODE_SIGNING_CERTIFICATE`: protected code-signing certificate location accepted by electron-builder.
   - `TARANGINI_CODE_SIGNING_PASSWORD`: certificate password.
4. Protect `main`: require pull requests, passing `Verify Tarangini`, and two-factor authentication for administrators.
5. Tag an approved commit, for example `v1.2.1`. The release workflow runs the full review suite, signs the Windows NSIS installer, then publishes the installer, `latest.yml`, and blockmap to the public update repository.

Never enter the update token or code-signing password in `package.json`, a local config file, or a customer computer.

## Safe rollout protocol

1. Verify the release in a test Main System and one test Client System.
2. Confirm database backup and restore tests are current.
3. Main System owner stages the release during a quiet period after checking client queues and conflicts.
4. Clients sync first, download the verified update, and select **Restart and Install**.
5. Confirm app version, database schema, and sync status on every client before expanding the rollout.
6. Keep the previous signed installer for recovery. Do not roll back a database migration after new work has been recorded; restore the pre-upgrade backup instead.

## Security properties

- `electron-updater` reads release metadata generated by electron-builder and checks its SHA-512 artifact hash.
- The stable workflow requires an Authenticode certificate issued to Tarangini before it can publish.
- Updates are disabled in development, service mode, and when `TARANGINI_DISABLE_AUTO_UPDATE=1` is configured.
- Automatic download and installation are disabled. Update availability is automatic; download and restart remain deliberate user actions.
- Client installation is refused when the offline queue has pending or conflicted work.

## Operational data sync is separate

GitHub version updates do not carry invoices, payments, ledgers, stock, jobs, customer details, uploads, attachments, backups, or user credentials. Those records continue to use the Tarangini Main System, authenticated APIs, and the existing offline queue protocol.
